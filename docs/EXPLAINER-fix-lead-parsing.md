# LeadHub — разбор правок: почему не находились лиды и что починено

> Это разбор первой порции правок к LeadHub. Читается как инженерный разбор:
> сначала контекст, потом суть, потом код, проверка и альтернативы. Отдельно в
> конце — что делать дальше и мини-квиз для самопроверки.

## TL;DR

Лиды не находились по трём независимым причинам, и все три складывались в «0 лидов»:

1. В поисковый запрос Instagram подмешивалось контактное слово («вотсапп»/«WhatsApp»),
   из-за чего `topsearch` искал буквально «глэмпинг новосибирск вотсапп» и не находил
   бизнес-аккаунты.
2. Три фильтра на панели (сайт в шапке, отсев тренеров/блогеров, regex ниш-исключений)
   **вообще не были подключены** к движку — галочки в интерфейсе ничего не делали, а
   самый строгий фильтр «есть сайт → отсеять» всегда был включён и резал реальные бизнесы.
3. Списки ниш и городов не прокручивались, кнопка «Остановить» висела всегда, а статус
   прогона путал.

В этой порции починены пункты, которые можно проверить юнит-тестами и статическим
разбором. Что осталось (импорт cookies из браузера, выбор VPN на старте прогона,
«6 кнопок», а также спуфер железа/виртуалка под WhatsApp) — вынесено в раздел
«Что дальше» с честной оценкой выполнимости.

> ⚠️ Важно про среду: в песочнице, где готовились правки, **нет .NET 10 SDK и доступа
> к NuGet**, поэтому я не мог выполнить `dotnet build` / `dotnet test`. Правки и тесты
> написаны и вычитаны, но их нужно прогнать на твоей Windows-машине (`dotnet test`).
> Ниже — точная инструкция.

## Background (контекст)

### Для тех, кто хочет с нуля

LeadHub ищет локальные бизнесы в Instagram и готовит для них тексты (писать ты будешь
вручную). Внутри — три слоя:

- **Core** (`LeadHub.Core`) — вся логика без интерфейса: разбор VPN-ссылок, движок
  парсинга, квалификация профилей, база SQLite. Кроссплатформенный, покрыт тестами.
- **App** (`LeadHub.App`) — WPF-интерфейс (только Windows): вкладки VPN, Аккаунты,
  Панель парсинга, Прогон, Лиды, Статистика, Настройки.
- **sing-box** — внешнее ядро, которое поднимает локальные SOCKS5-прокси
  (`127.0.0.1:108xx`) поверх твоих VLESS-VPN. Каждый «слот» = отдельный прокси-порт =
  отдельный IP.

Поток данных при прогоне такой:
`план запросов → topsearch (поиск кандидатов) → web_profile_info (полный профиль) →
квалификация (фильтры) → запись лида в БД`.

> ℹ️ Определение: **discovery** — этап, где по запросу «ниша + город» Instagram
> возвращает список аккаунтов-кандидатов. **Квалификация** — этап, где каждый кандидат
> проверяется по фильтрам (город РФ, размер аудитории, свежесть, наличие мессенджера
> и т.д.). Лид сохраняется, только если кандидат прошёл ВСЕ фильтры.

### Узкий контекст правки

Ключевой класс discovery — `ParseEngine.BuildQueryPlan`: он строит список поисковых
фраз (ниша × город). Ключевой класс квалификации — `Qualifier` в `Qualification.cs`:
он собирает список «причин отсева»; если причин нет — профиль становится лидом.
Настройки поиска приходят из `ParsePreset` (что заполняется на «Панели парсинга»), а в
движок передаются через `ParsePreset.ToOptions()` → `ParseOptions`.

Именно в стыке `ParsePreset → ParseOptions → Qualifier` и была дыра: часть настроек до
движка не доходила.

## Intuition (суть на пальцах)

### Симптом 1: «вотсапп» в запросе

Представь, что ты ищешь в поиске Instagram не «глэмпинг новосибирск», а «глэмпинг
новосибирск вотсапп». Instagram `topsearch` — это поиск по именам/никам аккаунтов, а не
полнотекст. Аккаунтов с «вотсапп» в имени почти нет → выдача пустая. Раньше код к каждой
фразе приклеивал по 2–3 контактных слова:

```
«кухни на заказ казань WhatsApp»
«кухни на заказ казань ватсап»
«кухни на заказ казань вотсап»
```

Это одновременно и мусорило запрос, и в статусе выглядело как та самая «каша с приписками
вотсапп». Правильно так: искать «кухни на заказ казань», а WhatsApp/Telegram — это
**фильтр** на этапе квалификации (какой мессенджер требовать), а не часть запроса.

### Симптом 2: мёртвые галочки

На панели есть тумблеры «Отсев тренеров/блогеров», «Исключить ниши (regex)» и
подразумеваемый «профиль с сайтом». Но `ParsePreset.ToOptions()` передавал в движок
только пороги подписчиков/постов/возраста. Три фильтра терялись по дороге. Следствие:

- `site_or_landing_in_profile` добавлялся **всегда** → любой бизнес, указавший сайт в
  шапке, отсеивался. А это очень много нормальных бизнесов.
- Галочка «отсев тренеров» ничего не выключала (отсев всегда был на).
- Поле regex-исключений не применялось нигде.

На маленькой выдаче из симптома 1 этот сверхстрогий фильтр добивал остаток — и на выходе
стабильный ноль.

## Code (что изменено)

### 1. Запрос = «ниша + город», без контактных слов

`LeadHub.Core/Parser/ParseEngine.cs`:

```csharp
// было: foreach (var term in terms.Take(3))
//           tasks.Add(new SearchTask($"{phrase} {city} {term}", ...));

void Add(string query, string niche, string group, string city)
{
    query = query.Trim();
    if (query.Length > 0 && seen.Add($"{city}::{query}"))
        tasks.Add(new SearchTask(query, niche, group, city));
}

foreach (var niche in niches)
    foreach (var phrase in niche.Phrases)
        Add($"{phrase} {city}", niche.Label, niche.Group, city);
foreach (var keyword in preset.CustomKeywords)
    Add($"{keyword} {city}", keyword, "Свои ключевые слова", city);
```

Заодно удалён теперь ненужный класс `ContactQueryTerms` и добавлена дедупликация
запросов на город.

### 2. Фильтры панели реально доходят до движка

`ParseOptions` получил три поля, `ParsePreset.ToOptions()` их прокидывает, а `Qualifier`
их уважает:

```csharp
if (bioSite.Found && _options.ExcludeSiteInProfile) reasons.Add("site_or_landing_in_profile");
if (_options.UsePersonalReject && PersonalRejectRe.IsMatch(combined)) reasons.Add("personal_or_trainer_profile");
if (_excludeNicheRe != null && _excludeNicheRe.IsMatch(combined)) reasons.Add("excluded_niche");
```

Regex ниш-исключений компилируется один раз; некорректный regex просто игнорируется (не
роняет прогон). Тот же тумблер «сайт в шапке» теперь есть и на панели парсинга.

### 3. UI: прокрутка и кнопка «Остановить»

- Списки ниш и городов обёрнуты в `ScrollViewer` (у `ItemsControl` нет собственной
  прокрутки, поэтому при `MaxHeight` контент просто обрезался — отсюда «не листается вниз»).
- Кнопка «Остановить» теперь отключается, когда прогон не идёт (через `CanExecute`), а
  состояние «идёт/остановлен» переключается по событию `RunStarted`.

## Verification (как проверить)

Я добавил/поправил юнит-тесты в `LeadHub.Core.Tests/CoreTests.cs`:

- `BuildQueryPlan_QueryIsNichePlusCity_NoContactTerms` — в запросах нет контактных слов,
  город в конце, дублей нет.
- `BuildQueryPlan_CustomKeyword_IsCombinedWithCity` — своё ключевое слово корректно
  склеивается с городом.
- `Qualify_SiteInBio_AllowedWhenExclusionOff`, `Qualify_PersonalProfile_AllowedWhenRejectOff`,
  `Qualify_ExcludedNicheRegex_Rejects`, `Qualify_InvalidExcludeRegex_IsIgnored` — тумблеры
  реально влияют на результат.

Прогнать на Windows (в песочнице .NET недоступен):

```
dotnet test LeadHub.Core.Tests
```

Ожидается: все тесты зелёные. Затем `dotnet run --project LeadHub.App`, вкладка «Панель
парсинга» → списки ниш/городов должны листаться; вкладка «Прогон» → «Остановить»
неактивна, пока прогон не запущен.

> ⚠️ Честная оговорка: правки discovery/фильтров сильно повышают шанс, что лиды пойдут,
> но живой поиск всё равно зависит от валидных cookies аккаунта и рабочего прокси. Это
> нельзя проверить в песочнице — нужен твой прогон на 1 нише + 1 городе с живым аккаунтом.

## Alternatives (альтернативы)

**Как искать кандидатов.**

| Оставить topsearch (сделано) | Перейти на hashtag/location-endpoints |
| --- | --- |
| ➕ минимальный дифф, эндпоинт уже в коде | ➕ часто больше релевантных бизнесов |
| ➕ не трогаем архитектуру | ➕ можно искать по гео-тегам города |
| ➖ выдача по нику/имени, уже небогатая | ➖ новые эндпоинты, выше риск лимитов |

**Фильтр «сайт в шапке».**

| Сделать тумблером (сделано) | Убрать совсем |
| --- | --- |
| ➕ по умолчанию логика скилла сохранена | ➕ максимум лидов |
| ➕ можно ослабить, если лидов мало | ➖ теряем фокус «бизнес без сайта» |
